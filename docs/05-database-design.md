# 1. Purpose

This document defines the logical and physical database design for Developer Platform Version 1.

It serves as the implementation reference for the persistence layer and describes the structure of the relational database, entity relationships, constraints, indexes, and design decisions.

The objectives of this document are:

- Design a scalable relational schema
- Maintain data integrity
- Support efficient querying
- Minimize data duplication through normalization
- Establish standards for future modules


# 2. Database Overview

Developer Platform uses PostgreSQL as its primary relational database.

Version 1 contains five core business entities:

- Users
- Workspaces
- Projects
- API Keys
- Short URLs

These entities support the platform's authentication, project management, and URL Shortener services.

# 3. Database Design Principles

The database follows the principles below.

## UUID Primary Keys

All business entities use UUID as the primary key.

Reasons:

- Prevent predictable identifiers
- Support distributed systems
- Enable application-level ID generation
- Simplify future migration to microservices

---

## Application Generated IDs

UUIDs are generated by the Spring Boot application instead of PostgreSQL.

Reasons:

- Database independence
- IDs available before persistence
- Easier testing
- Better support for distributed architectures

---

## Normalization

The schema follows Third Normal Form (3NF) to minimize data duplication and maintain data integrity.

---

## Auditability

Every business table includes audit columns to track creation, updates, and deletion.

---

## Referential Integrity

Relationships between entities are enforced using foreign key constraints.

---

## Soft Delete

Business entities are soft deleted using the `deleted_at` column instead of physical deletion.

This preserves historical records and supports auditing.

# 6. User Table

## Business Purpose

The `users` table stores authentication and profile information for every registered user of the Developer Platform.

Each user owns one or more workspaces.

---

## Table Definition

| Property | Value |
|----------|-------|
| Table Name | users |
| Primary Key | id (UUID) |

---

## Columns

| Column | Type | Nullable | Default | Description |
|---------|------|----------|----------|-------------|
| id | UUID | No | Generated by Application | Primary Key |
| first_name | VARCHAR(100) | No | - | User first name |
| last_name | VARCHAR(100) | Yes | NULL | User last name |
| email | VARCHAR(255) | No | - | Login email |
| password_hash | VARCHAR(255) | No | - | BCrypt password hash |
| phone_number | VARCHAR(20) | Yes | NULL | Optional phone number |
| email_verified | BOOLEAN | No | FALSE | Email verification status |
| last_login_at | TIMESTAMPTZ | Yes | NULL | Last login |
| status | ENUM | No | ACTIVE | User status |
| created_at | TIMESTAMPTZ | No | NOW() | Record creation |
| updated_at | TIMESTAMPTZ | No | NOW() | Record update |
| deleted_at | TIMESTAMPTZ | Yes | NULL | Soft delete |

---

## Constraints

- Primary Key(id)
- Unique(email)
- Unique(phone_number)
- NOT NULL(first_name, email, password_hash)

---

## Index Strategy

- PRIMARY KEY(id)
- UNIQUE(email)
- UNIQUE(phone_number)
- INDEX(status)
- INDEX(created_at)

---

## Relationships

One User

↓

Many Workspaces

---

## Design Decisions

- UUID prevents predictable identifiers.
- Passwords are stored using BCrypt.
- Email is used for authentication instead of username.
- Soft delete preserves historical data.

# 12. Relationships

The database follows a hierarchical ownership model.

| Parent Entity | Child Entity | Relationship |
|--------------|--------------|--------------|
| User | Workspace | One-to-Many |
| Workspace | Project | One-to-Many |
| Project | API Key | One-to-Many |
| Project | Short URL | One-to-Many |

### Relationship Rules

- Every Workspace belongs to exactly one User.
- Every Project belongs to exactly one Workspace.
- Every API Key belongs to exactly one Project.
- Every Short URL belongs to exactly one Project.
- Foreign key constraints enforce referential integrity.
- Ownership is derived through parent-child relationships to avoid redundant data storage.

# 13. Index Strategy

Indexes are created based on expected query patterns to improve read performance while minimizing unnecessary write overhead.

| Table | Index | Purpose |
|--------|-------|---------|
| users | PRIMARY KEY(id) | Primary key lookup |
| users | UNIQUE(email) | Fast user authentication |
| users | UNIQUE(phone_number) | Prevent duplicate phone numbers |
| users | INDEX(status) | Filter active users |
| workspaces | PRIMARY KEY(id) | Primary key lookup |
| workspaces | INDEX(user_id) | Retrieve user workspaces |
| workspaces | UNIQUE(user_id, name) | Workspace name uniqueness within a user |
| projects | PRIMARY KEY(id) | Primary key lookup |
| projects | INDEX(workspace_id) | Retrieve workspace projects |
| projects | UNIQUE(workspace_id, name) | Project name uniqueness within a workspace |
| api_keys | PRIMARY KEY(id) | Primary key lookup |
| api_keys | INDEX(project_id) | Retrieve project API keys |
| api_keys | UNIQUE(key_prefix) | Fast API key lookup |
| short_urls | PRIMARY KEY(id) | Primary key lookup |
| short_urls | UNIQUE(short_code) | Fast URL redirection |
| short_urls | INDEX(project_id) | Retrieve project URLs |
| short_urls | INDEX(expires_at) | Scheduled cleanup of expired URLs |

### Indexing Guidelines

- Create indexes only for frequently queried columns.
- Avoid indexing every column to reduce storage and write overhead.
- Composite indexes are used where business rules require scoped uniqueness.
- Indexes should evolve based on production query patterns.

# 14. Constraints

The database enforces the following constraints to maintain data integrity.

## Primary Keys

Every table uses a UUID primary key.

## Foreign Keys

- workspaces.user_id → users.id
- projects.workspace_id → workspaces.id
- api_keys.project_id → projects.id
- short_urls.project_id → projects.id

## Unique Constraints

- users.email
- users.phone_number
- workspaces(user_id, name)
- projects(workspace_id, name)
- api_keys.key_prefix
- short_urls.short_code

## NOT NULL Constraints

Mandatory business fields are marked as NOT NULL to ensure data completeness.

## Enum Constraints

Status columns use predefined enum values to maintain valid entity states.

# 16. Soft Delete Strategy

Developer Platform uses soft deletion instead of permanently removing records.

Instead of executing:

```sql
DELETE FROM users WHERE id = ?;
```

the application updates:

```sql
UPDATE users
SET deleted_at = NOW()
WHERE id = ?;
```

### Benefits

- Preserves historical records.
- Maintains referential integrity.
- Supports account recovery.
- Enables auditing and analytics.
- Prevents accidental data loss.

Application queries should exclude records where `deleted_at IS NOT NULL` unless historical data is explicitly requested.

# 18. Design Decisions

The following design decisions were made during the database design phase.

| Decision | Reason |
|----------|--------|
| PostgreSQL | Mature, ACID-compliant relational database with excellent indexing and JSONB support |
| UUID Primary Keys | Prevent predictable identifiers and support distributed systems |
| Application-Generated UUIDs | Database independence and IDs available before persistence |
| Third Normal Form (3NF) | Reduce redundancy and improve data integrity |
| TIMESTAMPTZ | Timezone-aware timestamps for cloud-native deployments |
| Composite Unique Constraints | Enforce business rules within entity ownership boundaries |
| BCrypt Password Storage | Secure password hashing with adaptive cost factor |
| SHA-256 API Key Hashing | Prevent storage of plaintext API keys while enabling secure authentication |
| Soft Delete | Preserve historical records and maintain referential integrity |
| Hierarchical Ownership Model | Normalize relationships and eliminate duplicate ownership data |
| Foreign Key Constraints | Enforce referential integrity between business entities |
| Query-Driven Indexing | Improve performance based on expected access patterns while avoiding unnecessary indexes |
